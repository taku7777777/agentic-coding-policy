## 1. 構造

```
<repo>/
├── src/ …                        コード等
├── work/                         C。root 直下(§2)
│   └── <YYYY-MM-DD>-<slug>/
└── docs/                         権威ある場所(文書)。無いリポジトリでは作る
    ├── *.md, <topic>/*.md        L — 現在形の本体
    ├── adr/NNNN-<slug>.md        A — 特別容器(決定)。閉じた集合(§4)
    ├── records/<YYYY-MM-DD>-<slug>.md   A — 汎用容器(それ以外の時点の記録すべて)
    └── assets/                   L 文書に従属する非文書(画像・データ)
```

**判別規則**(スニペットに載る完全形):

- **A**: `docs/records/**`・`docs/adr/**` の中にある、**または冒頭に `種別: 記録` を持つ**ファイル
  —— 追記。上書きせず §6 の注記方式
- **C**: `work/**` —— 権威なし
- **L**: それ以外 —— 直接上書きしてよい

マーカーの位置づけ: **書かない・見たら尊重**。新規の A にマーカーは付与しない(場所が宣言する)。
ただし読み手の判別では引き続き A のシグナルとして尊重する —— 未移行リポジトリ・移行窓・
第三者採用リポジトリ・ツール固定パス(§3.3)の既存マーカー付きファイルを、パス規則が
L と誤断して上書きする事故を防ぐ(矛盾時は A 側 = 安全側に倒す)。
新規付与が残るのは §3.3(ツール固定パスのタスク完了時)のみ。

**位置は docs/records/ に一本化する**(前版の「docs/ が無ければ root 直下」原則は撤回)。
docs/ を持たないリポジトリでは docs/ を作る。理由: (i) 前版の判別規則は root 形態を字義に含まず、
移行第1号の自リポジトリで移行後の A が L 判定になる自己破壊があった (ii)「L 文書の権威ある場所の直下」
は自リポジトリ(docs/cowork/ が実在し L は root)で既に決定不能だった (iii) root `records/` は
データディレクトリ名として一般的で、docs/ を持たないコード系リポジトリほど既存名と衝突しやすい。
一本化により判別は文字どおり単一のパスパターンになり、root の予約名は work/ 1つのままになる。

## 2. work/ を docs/ に入れない理由(裁定1への回答)

1. **work/ は文書専用ではない。** 使い捨てスクリプト・実行ログ・生成データも入る(§3)。docs/ 配下に
   置くと「docs/ = 人が読む文書」の意味が濁り、docs サイトビルド・検索・レビュー対象に中間物が混入する
2. **権威の境界が一刀で切れなくなる。**「work/ 以外 = 権威あり」が「docs/** ただし docs/work を除く」
   という中抜きになる。仕様修理0回の機構の単純さを守る
3. **パイロット継続性。** root work/ は配布済み・観測中。壊れていない側を動かさない

records/ を docs/ に入れる利点: A は文書なので文書の権威ある場所に住むのが意味的に正しい /
L と同じ木に収まり隣接性の懸念が緩和 / docs/adr/ と兄弟になり「adr = records から特別昇格した種別」が
構造に現れる。docs サイトを持つリポジトリでは records/ をビルド除外してよい(導入手順に含める)。

## 3. 本流到達の規則(範囲を限定 — 敵対レビュー指摘4の裁定)

規範は**完了の宣言**についてのみ:

- **「実施済み」と記録・報告してよいのは本流(master 等)到達後**。実施記録は本流側のコミットを指す。
  未マージ時点の応答内報告(§5.3 の1行報告)は「変更パス + 本流到達待ち」と書く —— 報告自体は妨げない
- **単独の小さな PR を推奨するのは管理作業(移行・遡及注記・記録だけの追加)に限る**。
  タスク内の形態2 昇格(A 移動 + L 参照文)は機能 PR への同乗を明示的に許す —— 全タスクの PR 二重化は
  求めない。master 直コミット運用のリポジトリではこの推奨は空対象であり、何も要求しない
- **§12 監査は origin/master を読む**。未マージの昇格は「観測できない」に分類する(成功とも失敗とも数えない)

根拠(実測): マーカー付与 `2ae04ed`(07-30)は**マージ済み**ブランチに積まれ合流経路を失い、実施記録には
「実施済み」と記録され、約2日後に同一パッチの重複適用 `d078460` が発生、master は現在も未到達。
第5巡-1「版番号の発行は master 上の本書に限る」と同じ教訓の、完了宣言への一般化である。

## 4. adr の統治規則(裁定6)+ 採番規則の移設

- 特別容器は「多くのシチュエーションで必要」が実証された種別に限る**閉じた集合**とし、**policy 本体が
  版として定義する**。リポジトリ・タスク単位で新設しない。現時点の集合: **`docs/adr/` のみ**
- 将来の特別昇格の基準: (i) 複数リポジトリで反復発生 (ii) 種別固有の書式・参照規約が確立
  (iii) policy 改訂(版)としてのみ追加
- §5.6 の ad-hoc 容器新設規定(`docs/BENCH.md` 等)は削除
- **採番規則の移設**(§5.6 削除で置き場が消えるため本節へ): adr/ の `NNNN` は既存最大値+1。
  **並列時の採番・records/ 新設は親(オーケストレータ)のみが行う**。
  adr/ の連番衝突は v7 でも残る —— F4 が「消滅」するのは records/ 分だけである(§7 表を訂正)

## 5. 命名とフォーマット(裁定4)

- 新規レコード: `docs/records/<YYYY-MM-DD>-<slug>.md`
  - **日付は、work/ からの昇格なら元の work/ ディレクトリの日付を引き継ぐ**(対応関係が名前で残る)。
    work/ を経ない直書き(ADR 相当の記録等)は記録の成立日
  - 並列・複数観点のときは work/ と同じく `<YYYY-MM-DD>-<担当>-<slug>.md` で一意にする
    (同日同主題の silent clobber 防止 —— A 容器内の上書きは検知機構が無いため命名で防ぐ)
- **集合型レコード(名詞句の追記ファイル)は置かない**(前版から変更 —— 裁定3「1ファイル肥大を避ける」
  との自己矛盾を解消)。実測値の蓄積は「1計測 = 1日付レコード」+ **L 側の手維持集計表**に分解する
- **射程フィルタを v7 に同梱する**(先送りしない —— records/ は摩擦の少ない汎用スロットなので、
  過剰昇格への防壁を同時に入れる): 「**タスク限りの記録は work/。records/ に入るのは、
  今後の判断が依拠しうる記録だけ**」。§12 監査では参照文の無い records/ 直書きファイルを
  「要目視」の第3分類として扱う
- 冒頭ヘッダ標準: `日付: / 状態:`(+ `対象:` 任意)。主要種別(レビューFB / 決定 / 調査findings)の
  最小テンプレを §5.5 の例示に付す。置き場のタクソノミーは作らない(置き場は records/ 一択)
- **records/ に README・index を置かない**(work/README.md と同じ自己矛盾)。洗い出しは L 側の
  手維持対応表(実例: metsuke 08-dashboard.md §17)
- **A に従属する資産は records/ 内に置く**(`docs/records/<YYYY-MM-DD>-<slug>-<name>.png`、
  複数なら `docs/records/<YYYY-MM-DD>-<slug>/` のディレクトリ型も可)。パス判別が資産にもそのまま効き、
  当時形の証拠が L 扱いで再生成・上書きされる事故を防ぐ。**docs/assets/ は L 文書に従属する資産専用**
  (F9 の解消はこの分担で成立)

## 9. 残る限界

1. 分類判断そのものは残る(§10-5)。消えるのは「判断結果の記録し忘れ」。射程フィルタとテンプレで緩和
2. **CHANGELOG のリリース済み節の保護が規約から消える**(裁定3 の受容トレードオフ。
   実測サンプルに実運用の CHANGELOG が無いことが受容の根拠。運用したいリポジトリは
   リリースごとに records/ へ切り出す実践を任意で採れる)
3. マーカーは読み手側に1行残る(後方互換)。「判別はパスのみ」ではなく
   「**書く側はパスのみ・読む側はパス+レガシーシグナル**」が正確な表現
4. 主題隣接性は docs/ 内で1階層。L 側対応表で補う(裁定5)
5. 複数リポジトリ跨ぎの記録の置き場は本設計でも未解決(第6巡候補のまま)
