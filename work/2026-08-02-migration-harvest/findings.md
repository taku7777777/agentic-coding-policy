## 規範の穴(第10版で修正)

### 穴1: §12.1 は並行作業中のリポジトリでの移行を想定していない【実害あり】

git mv は自動でステージされる。sekisho で mv とコミットの間に並行セッションのコミットが挟まり、
rename 39件が無関係なコミット(30d61ff「fix(p5): U-27…」)に混入した。§12.1 には
「未マージブランチは先に合流」はあるが、稼働中セッションとの index 競合への言及が無い。
→ 対処は手順の性質(留意事項)なので migration.md へ。「mv → コミットを一連で行う/静穏時に実施」

### 穴2: §12.1 に「被参照の全数列挙」の手順が無い【実害あり】

「L 側の参照リンクを更新し」とあるが、参照元の網羅方法が未規定。調査は主要 L 文書からの参照だけを
洗い、活動中4文書(p4-findings / p5-plan / p4-m3-plan / design/11)からの流入参照を見落として
移動後に壊れリンク11件が発生した(事後修正済み)。列挙の「固定リストを使わない」原則と同型:
発見は列挙ではなく走査で行う。
→ 不変条件として §12.1 に1行(「移動対象の basename を repo 全体で grep して被参照を全数列挙」)。
具体コマンド・パターンは migration.md へ

### 穴3: 「本流」の定義が remote 無し・複数ブランチ運用で決まらない

sekisho は main(合流のマイルストーン先)と sekisho-m1(事実上の幹)の二層。§5.3/§12.2 の
「本流(origin/master 等)」ではどちらか確定できず、「sekisho-m1 到達済み・main 合流待ち」という
即席の記載で凌いだ。
→ §5.3 に定義を1文(remote があれば origin の既定ブランチ / 二層あるリポジトリでは到達を
ブランチ名で記す)

### 穴4: §3.3 の射程が「読み取りパス固定」に限定されている

skills の quality/results/<日付>/ は書き込み側をツールが固定する記録ディレクトリで、
§3.3 を類推適用して移行対象外と裁定した(スイープ記録)。条文は「読み取りパスを固定」なので
根拠が半歩ずれる。§12.1 側は既に「ツールがパスを固定する成果物」と書いており、§3.3 と不整合。
→ §3.3 と §11 スニペットの文言を「パスを固定」(読み書きを問わない)に統一。
**スニペットに触れるため v10 で再配布が必要**(§12.2 全数)

## 構成の改善(ユーザー裁定 2026-08-02)

移行(§12.1)は1リポジトリ1回きりで常時参照される内容ではない。手順の詳細・留意事項を
**migration.md(root・L)に切り出し**、policy.md §12.1 は不変条件だけを保持して参照する。
migration.md は非規範(規範は policy.md §12 が正)とし、§11 の版なし更新可リストに加える
—— 留意事項は経験で成長するので、版の重さから切り離す。

## 記録どまりの知見(規範化しない)

1. **「1回きり移行」は実際には段階的になる**: 活動中11本の除外・16〜19 のクラスタ保留のように、
   部分移行+名指し保留で閉じるのが現実。保留条件を記録に残す実践は現行規約の範囲内で成立した
   → 保留の名指し記録は §12.1 の不変条件に昇格(穴2と同時に)、ヒューリスティックは migration.md
2. **単一リポジトリの内部証拠だけでは導入判断を誤る**: 調査エージェントの推奨を2件覆した
   (monitoring-ex = metsuke の前身 / co-working = 実験進行中)。後継・重複関係はリポジトリ横断でしか
   見えない → migration.md の事前調査節へ
3. **凍結判定のヒューリスティック**: 「ステータス: 確定」宣言があっても直近に変更があるものは
   動かさない(最終変更の近さ = hot の信号)→ migration.md へ
